# Kirana Store — Project Conventions

## Stack
Next.js 16 (App Router) + React 19 + TypeScript + Tailwind v4 + shadcn/ui
+ Prisma + MySQL + TanStack Query + axios. Full stack lives in this one
Next.js app. No tRPC — TanStack Query talks to this app's own Route Handlers
via axios (mirrors the `weave` project's pattern, not repo-mind/project-iq's
tRPC pattern).

## Code style
- **Arrow functions only, no `function` declarations.** Every component,
  hook, api function, and Route Handler export is a `const` arrow-function
  binding: `const ComponentName = () => {}`, `const useThing = () => {}`,
  `export const POST = async (request: Request) => {}`. This includes
  default exports that need a name for a doc comment to attach to (declare
  the `const`, then `export default ThatConst` on its own line) and
  `proxy.ts`'s export.
- **JSDoc on every hook and component.** A short `/** ... */` comment above
  the declaration explaining what it does and how to use it, with a
  `@param` line per prop (components) or argument (hooks/functions that
  take one). Example:
  ```ts
  /**
   * Mutation hook for logging in. Calls POST /api/auth/login and redirects
   * to /dashboard on success.
   */
  export const useLogin = () => { ... }

  /**
   * Wraps the app in a TanStack Query QueryClientProvider.
   * @param children - The subtree to render inside the provider.
   */
  const QueryProvider = ({ children }: { children: React.ReactNode }) => { ... }
  ```
- **Comment non-obvious variables/functions elsewhere too** — a short `//`
  above a piece of logic whose *why* isn't obvious from its name (a magic
  number, a workaround, a non-default TTL). This project intentionally
  comments more than typical minimal-comment style guidance — don't skip
  the JSDoc or the `@param` tags because the code "looks self-explanatory."
- **Exception: shadcn-generated files stay as-is.** `src/components/ui/*`
  and any other file generated by `npx shadcn add` keep whatever style
  they were generated with (including `function` declarations) — never
  hand-edit generated files, style included. This convention applies only
  to hand-written app code (`src/app/`, `src/features/`, `src/lib/`,
  `src/components/providers/`, `src/proxy.ts`).

## Folder structure (per feature: auth, products, billing, bills, dashboard, reports)
- `src/app/` — routing only (page/layout/loading/error). Renders a feature's
  `*-view.tsx`; no Prisma/axios calls here directly.
- `src/app/api/<resource>/route.ts` — Route Handlers; the backend TanStack
  Query calls. Always call `verifySession()` (from `lib/dal.ts`) before
  touching Prisma.
- `src/features/<name>/api/index.ts` — axios functions calling this app's
  own `/api/*` routes, typed against `types.ts`. One function per endpoint.
- `src/features/<name>/hook/use-<name>.ts` — TanStack Query hooks wrapping
  the api functions (`useQuery`/`useMutation`), one file per feature with
  every query and mutation for that feature colocated in it.
- `src/features/<name>/types.ts` — flat file of request/response types.
- `src/features/<name>/_components/` — feature UI; the page-level
  composition is named `<name>-view.tsx` and is what `app/.../page.tsx`
  renders.
- `src/features/auth/` follows the same api/hook pattern as every other
  feature (login and logout are Route Handlers + axios + TanStack Query
  mutations, not Server Actions) — no exception here, despite Next.js's own
  docs suggesting Server Actions for auth forms.
- Not every feature needs its own `api/`/`hook/` — a feature that only
  aggregates other features' data (e.g. `dashboard` composing
  `useAllProducts`/`useAllBills` from their own features) can leave
  `hook/` empty and import those hooks directly instead of duplicating them.
- `src/components/ui/` — shadcn primitives only. Add with
  `npx shadcn add <name>`; never hand-edit generated files.
- `src/components/layout/` — shared shell UI (sidebar, topbar).
- `src/components/providers/query-provider.tsx` — the `QueryClientProvider`,
  `'use client'`, `QueryClient` created via `useState(() => new QueryClient())`.
  Imported once in the root `layout.tsx`.
- `src/lib/` — cross-cutting singletons: `db.ts` (Prisma client), `session.ts`,
  `dal.ts`, `utils.ts`.
- `prisma/schema.prisma` — all models in one file.

## Data fetching (TanStack Query + axios)
Mirrors the `weave` project's pattern exactly — read `D:\AI+Full stack
projects\weave` for a live reference if in doubt.

- **No shared axios instance.** There is no `lib/axios.ts`, no baseURL, no
  interceptors. Every `api/index.ts` does `import axios from "axios"`
  directly and calls same-origin relative paths (`"/api/products"`), since
  the client and the API live in the same Next.js app.
- **api functions** (`features/<name>/api/index.ts`): one exported `async`
  function per endpoint, named after the action, verb-first (e.g.
  `createProduct`, `deleteBill`, `allProducts`). A single extra param is a
  bare scalar (`getProductStock(productId: string)`); multiple params are
  one destructured object. Always type the axios call generic
  (`axios.post<CreateProductResponse>(...)`), pull out `{ data }`, and
  return `data` (or a narrowed sub-field). `DELETE` with a body uses
  `axios.delete(url, { data: {...} })`. A mutation's param object may carry
  a field the server never uses (e.g. a `productName`) purely so the
  hook's `onSuccess` can reference it without waiting on the response body.
  ```ts
  export const createProduct = async (input: CreateProductInput) => {
    const { data } = await axios.post<CreateProductResponse>("/api/products", input)
    return data
  }
  ```
- **Query hooks** (`features/<name>/hook/use-<name>.ts`): no query-key
  factory — keys are plain inline kebab-case string arrays
  (`["all-products"]`, `["product-stock", productId]`), params appended
  for parameterized queries. Query hooks accept an optional
  `options?: { refetchInterval?: number }` passthrough for polling, and
  thread `enabled` explicitly when a query shouldn't fire until some UI
  state is true. Use `keepPreviousData` for paginated lists to avoid
  flicker. Naming: `useGetX`/`useAllX`/`useX` for queries.
  ```ts
  export const useAllProducts = (options?: { refetchInterval?: number }) => {
    return useQuery({
      queryFn: allProducts,
      queryKey: ["all-products"],
      refetchInterval: options?.refetchInterval,
    })
  }
  ```
- **Mutation hooks**: named `use<Verb><Noun>` (e.g. `useCreateProduct`,
  `useDeleteBill`). Give every mutation a kebab-case `mutationKey` matching
  the action. `onSuccess` invalidates the relevant `queryKey`(s) via
  `queryClient.invalidateQueries`, then toasts success via `toast.add(...)`
  (`import { toast } from "@/components/ui/toast"`). `onError` always
  toasts via a per-file `getErrorMessage(error, fallback)` helper (copy it
  into each hook file rather than centralizing it):
  ```ts
  const getErrorMessage = (error: unknown, fallback: string) =>
    isAxiosError<{ error?: string }>(error) && error.response?.data?.error
      ? error.response.data.error
      : fallback

  export const useDeleteProduct = () => {
    const queryClient = useQueryClient()
    return useMutation({
      mutationFn: deleteProduct,
      mutationKey: ["delete-product"],
      onSuccess: (_data, { productName }) => {
        queryClient.invalidateQueries({ queryKey: ["all-products"] })
        toast.add({ title: "Product deleted", description: `${productName} was deleted.`, type: "success" })
      },
      onError: (error) => {
        toast.add({
          title: "Couldn't delete product",
          description: getErrorMessage(error, "Something went wrong deleting the product. Please try again."),
          type: "error",
        })
      },
    })
  }
  ```
- **Types**: response types live in `types.ts`, named `<Thing>Response`
  (e.g. `CreateProductResponse`, `ProductsResponse`), imported into both
  `api/index.ts` and `hook/use-*.ts` with `import type {...} from "../types"`.
  A Route Handler's response type should mirror exactly what that route
  returns.
- **Route Handlers**: `verifySession()` at the top, validate input,
  `try/catch` around Prisma calls, `NextResponse.json(data)` on success and
  `NextResponse.json({ error: "..." }, { status })` on failure.
- **Escape hatch**: a one-off, non-reusable call that isn't a feature-level
  data operation (e.g. a root-layout "ensure session is warm" ping) may call
  axios directly in a `useEffect`, bypassing the api/hook pattern — reserve
  this for genuine one-offs, not as a shortcut around writing a hook.
- No generic CRUD-hook factory (`createQueryHook`/`createMutationHook`) —
  every hook is written by hand per endpoint. Verbose but explicit; don't
  introduce an abstraction layer here.

## Auth (hand-rolled, no auth library)
- `src/lib/session.ts`: encrypt/decrypt the session payload with `jose`,
  set/delete the HTTP-only session cookie.
- `src/lib/dal.ts`: `verifySession()` is the real authorization boundary —
  call it at the top of every Route Handler and every protected
  page/layout that touches user data.
- `src/proxy.ts`: optimistic redirect only (cookie-presence check). Next.js
  16 renamed `middleware.ts` to `proxy.ts` — same behavior, new filename —
  and it must never be the only line of defense; enforcement happens in
  `verifySession()`.

## shadcn/ui
- This project uses the `base-vega` preset style (see `components.json`).
  Add components with `npx shadcn add <name>`, don't hand-write them.
- `TooltipProvider` (from `src/components/ui/tooltip.tsx`) must wrap the app
  in `layout.tsx` — several shadcn components use tooltips internally.
- `Toaster` (from `src/components/ui/toast.tsx`) must also wrap the app in
  `layout.tsx` — mutation hooks call the imperative `toast.add(...)` API,
  which needs a mounted `Toaster` to render anything.

## Environment
- Required vars: `DATABASE_URL`, `SESSION_SECRET`, `ADMIN_EMAIL`,
  `ADMIN_PASSWORD_HASH`. Keep `.env.example` in sync with `.env.local`.
- **`ADMIN_PASSWORD_HASH` gotcha**: Next.js's env loader (`@next/env`)
  expands `$name`/`${name}` sequences like shell variable substitution. A
  bcrypt hash (`$2b$10$...`) gets silently corrupted — everything up to the
  third `$` is stripped — unless every `$` in the value is escaped as `\$`
  in `.env.local`, e.g. `ADMIN_PASSWORD_HASH="\$2b\$10\$abc..."`. Verify a
  new hash actually round-trips with
  `node -e "require('@next/env').loadEnvConfig(process.cwd(), true); console.log(process.env.ADMIN_PASSWORD_HASH)"`
  before trusting it.

## Reuse over duplication
- Before writing a new component, hook, type, or helper, check whether one
  already covers it: `src/components/ui/` (shadcn primitives),
  `src/components/layout/` (shared shell), `src/lib/utils.ts` (formatting/
  helpers), `src/hooks/` (shared hooks), and other features' `_components/`
  for a piece that generalizes (e.g. a table, a dialog, an empty state).
- Shared UI that more than one feature needs (a data table shell, a
  confirm-delete dialog, a currency/date display) belongs in
  `src/components/` or `src/lib/utils.ts`, not copy-pasted into each
  feature's `_components/`.
- Within one feature, factor out repeated JSX/logic (e.g. the same form
  fields used by both create and edit) into a shared component/function in
  that feature rather than duplicating it across files.
